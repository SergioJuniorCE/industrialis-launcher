# UI Taste

- Wants repeated UI elements (cards/tiles in a grid or sidebar) to have normalized, fixed sizes: no element should grow taller than its siblings just because it carries extra content (e.g. an "Update available" line). Fix by moving the extra state into an overlaid icon/badge inside the existing footprint instead of stacking another text row. Confidence: 0.6
- Prefers compact icon affordances (badge, dot, small overlay button) over added text labels for status state; icons should be clickable to open the related action. Confidence: 0.55
- Chooses icons by literal semantics, not by generic "attention" iconography: an available update must use an up-arrow / download style icon, not a bell — a bell implies a notification/toast, and an update is not a notification. Confidence: 0.7
- For an available update the preferred glyph is a Lucide-style "download" mark (arrow pointing down into a line/tray) rather than a plain arrow-in-circle. Confidence: 0.5
- Conveys visual/icon intent with reference screenshots ("something like this" + image) and expects the implementation to match that reference closely instead of a free interpretation; the reference may also be another app named outright ("like in Prism Launcher") or both. Confidence: 0.6
- For managing a collection of items (e.g. mods in a modpack), prefers a single list with a checkbox per item that enables/disables it, over removal flows: rejected a Remove-button + confirm-dialog + separate "Removed by you" section design and asked for "a list of mods with check boxes and disable that one", citing Prism Launcher's mod list as the model. Confidence: 0.75
- Prefers non-destructive disable semantics over delete/quarantine for managed content: unchecking a mod should leave its file on disk (renamed to a disabled state) so the same click re-enables it, rather than deleting it or moving it to a hidden store. Confidence: 0.65
- When an approach is rejected, expects the rejected artifact to be fully removed (delete the unused asset/SVG, drop its registry entry) rather than left orphaned. Confidence: 0.55
- Controls (buttons, checkbox-like toggles, option/filter pickers) should have visible borders; treats borderless/ghost styling as a defect ("buttons are missing a border, idk why so many things in our app are missing borders") and expects an outlined variant to be used instead. Confidence: 0.75
- Rejects borderless "ghost" buttons for text-only controls (e.g. a toggle rendered as a bare "☐ Label" button); prefers a real checkbox/bordered control helper. Confidence: 0.6
- List rows / option rows should be left-aligned, not centered — text should start at the left edge (justify_start) even when the row spans full width. Confidence: 0.7
- When UI quality is called out ("looking a bit rough"), wants design work done through the Hallmark skill / its app-screen redesign references rather than ad-hoc tweaking. Confidence: 0.6
- Frames bad UI as "slop" and expects a deliberate hierarchy/holistic redesign pass over the touched surfaces (grouped sections, one visual container per list, uniform rows) rather than isolated style patches. Confidence: 0.55
- Wants list rows laid out as fixed columns so metadata stays put: trailing columns (date/status, then a dedicated check-mark column) get a fixed width and the selection indicator's slot is always reserved, so the date never shifts when a different row is selected. Confidence: 0.7
- Expects styling fixes to be applied consistently across sibling dialogs/screens (fix one dialog's borders/alignment and propagate the same treatment to equivalent dialogs) rather than patched in one place only. Confidence: 0.55
- Every context-menu / popover entry should carry an icon next to its label; notices and reports menus where icons are absent ("There are missing icons Add some") and expects all sibling menus (library, group, file, instance) to share the same icon + label layout rather than only the menu called out. Confidence: 0.6
- Wants live motion as progress feedback: when a process/operation is active, its loader icon should visibly spin/rotate so the user can see that work is happening, instead of a static glyph that reads as idle. Confidence: 0.6
- Progress/state indicators should be applied everywhere that state appears (toolbar button, list rows, compact dropdown row, detail header), not just the one instance in the screenshot. Confidence: 0.5
- Prefers information-dense detail screens over minimal ones — on a process/operation detail view more visible data is better ("the more shit we can show on that screen the better"): log pane, metadata strip (operation, elapsed, instance), line counts, copy affordance. Confidence: 0.6
- Values a "seamless" update/install experience: prefers non-blocking background work with progress surfaced persistently on the relevant object, and pushes back on anything where the user cannot see or keep working (blocking modals, silent work, thin distant indicators). Confidence: 0.5
- Progress for an active operation should be attached to the related status icon (a ring drawn around the icon) rather than a detached edge/bottom progress bar; complains when a process state is only shown by a thin bar away from the object it describes. Confidence: 0.6
- Explicitly asks for "pretty animations": expects polished motion (spring/eased interpolation) on progress and state changes instead of discrete jumps. Confidence: 0.6
- Wants shared style primitives rather than per-call-site styling: asks for "a baseline component for a button" that all buttons derive from (same height, radius, focus ring, 1px token border, variant-only color differences) instead of each screen hand-rolling its own look. Confidence: 0.6
- Treats missing borders as a global, systemic defect rather than a per-widget one ("a lot of borders are just missing from the whole UI") and expects a whole-app sweep over buttons, inputs, badges, cards and menu surfaces, not just the element in the screenshot. Confidence: 0.6
- Wants border restraint, not border saturation: borders are for structure (standalone dialog actions, filled/outline controls, badges, inputs, cards, dialogs) and not for boxing every control — corrected an over-broad fix with "I'm not saying to add borders everywhere, but it just needed a bit more borders", implying ghost buttons and rows living inside an already-bordered menu surface should remain borderless. Confidence: 0.8
- Structural dividers and section headers (e.g. the separator above a group of items) should NOT be bordered: a section separator reads as a plain rule/header, and giving it a 1px border counts as unwanted chrome ("the border on this section separator for the groups is not needed"). Confidence: 0.6
- Refines border feedback iteratively with screenshots pointing at specific elements that should NOT have gotten a border ("for example, these borders were not needed", "the border on this section separator is not needed"); expects the flagged elements reverted to borderless while the rest of the border work stays, not a wholesale undo. Confidence: 0.65
- Interactive rows and section dividers/headers must be colorless (fully transparent) at rest and only gain a background on hover: rejects a persistent gray/tinted row fill ("dont make the bg of the group divider gray, make it colorless but secondary on hover"). Confidence: 0.7
- The standard hover highlight for quiet rows is the secondary surface token (`theme.secondary()`), and every control inside such a row (collapse toggle, delete action) should share that same hover treatment so the row highlights as one unit rather than each control tinting differently. Confidence: 0.6
- Wants background operations to emit verbose, per-phase log lines (catalog fetch, resolve, cache, rollback prep, copy, restore, overlays, settings save, completion) so the process screen has a real trail rather than a couple of terse messages. Confidence: 0.5
